# 实现流程

> **已被替代（2026-11-05）**：本文件里的状态机、`base_commit`、`/handoff` 调用方式和验收命令格式都已废弃。
> 现行依据是 `doc/IMPLEMENTATION-PLAN.md`、`schemas/*.schema.json` 与 `handoffctl --help`。
> 本文保留作为早期流程设计的历史记录，其中的「谁做什么」仍然可读，但字段与状态以 schema 为准。

这份写的是「每一步做什么、谁做、什么条件算过」。不含实现代码。

角色：**前端**（发起与验收）、**后端**（执行与交付）。

原则：**git 是唯一必需通路。** 任务单和状态都放在交接仓里，前端推上去、后端拉下来、后端把结果推回来。这样丢不了东西，也不会有「消息发了但没收到」。

局域网里的 HTTP 服务是可选加速器，只用来把状态变化秒级推给前端。不装它，退化成探测仓库，慢几秒，流程照样成立。

---

## 零、前置条件

做之前先确认三件事，缺一件流程跑不通。

**1. 交接私有仓。** 单独一个 repo，只放任务单，不放业务代码。理由：它是审计日志，会被频繁 commit，混进业务仓库会污染历史。

```
handoffs/
  tasks/<id>.json     任务单，唯一真实来源
  archive/            已归档的
```

**2. dev 环境的版本标识。** 这是整套东西的支点，见第五节。没有它，验收就不知道验的是哪一版。

**3. 后端机器上有 `gh`（或 GitLab 的等效 CLI）和有效的登录态。** 合并走 API，不走本地 merge。

**4. （可选）后端机器的固定局域网 IP 和一个共享密钥。** 只有走 HTTP 加速才需要。DHCP 的地址一变全断，要么在路由器上绑 MAC，要么启动时把 IP 写进交接仓。要密钥是因为同网段不等于安全。

---

## 一、发起

**触发**：前端在 codex 会话里说「这块要后端做」。

**做什么**：从当前会话抽出四样，写成任务单，提交到交接仓。

抽的四样：

- **requirement**：字段级。哪个接口、什么方法、请求什么样、响应什么样、边界怎么办。不是复述需求，是写成后端能照着做的。
- **acceptance.checks**：可执行的验收命令，不是「跑一下看看」。
- **out_of_scope**：明确不做什么，防止后端顺手改别的。
- **base_commit**：前端当前 HEAD。后端基于它开分支，避免漂移。

顺带带上 `contract`（接口契约、类型定义）和 `repro`（报错、请求响应、截图）。

**写到哪**：`tasks/<id>.json`。id 用 `ho-YYYYMMDD-序号`，序号当天从 001 起，先看目录里有什么，别撞。

**不做什么**：不塞整段会话。几十万 token，后端读不完还费钱，而且里面混着无关内容。

**成功的标志**：`tasks/<id>.json` 存在，并且 push 成功。推上去就等于送达，不需要额外发通知。

**失败处理**：push 不通就是没权限或网络断了。任务单先留在本地，能推的时候再推。**不要改走别的通道发**——正文只有一份，在 git 里。

---

## 二、接收

**谁做**：后端机器上的进程。可以是常驻服务，也可以一开始就是人跑一条命令看仓库。

**顺序**：

1. 感知交接仓有新提交。轻量做法：每几秒 `git ls-remote` 看一眼，变了才真拉。一次两百毫秒，比拉整棵树省一个数量级。
2. 拉下来，扫 `tasks/` 里状态为 `open` 的单。
3. 校验必填字段。`requirement` 缺失的直接标 `failed` 并注明原因，不做「差不多就行」的兜底。
4. 查重。同一个 id 已在执行或已完成的，跳过。这是幂等，防止重复推或重试把同一个任务跑两遍。
5. 入队。

**权限由 git 保证**。能 push 交接仓的人才能发单，不需要额外的密钥校验。这是纯 git 通道比 HTTP 干净的地方。

**队列必须串行**。同一台机器同时跑两个 `codex exec`，两个都改同一个仓库，git 索引会打架。串行也顺带保证了部署不会并发顶掉。

**那 HTTP 服务还要不要**：要，但只为一件小事——把状态变化秒级推给前端（SSE）。不装它，前端靠探测仓库，慢几秒，流程一样成立。别为了它牺牲主通道的可靠性。

---

## 三、执行

**谁做**：后端机器上的进程拉起 codex。一开始完全可以由人手动跑，跑顺了再交给常驻进程。

**顺序**：

1. `git fetch`，然后基于 `base_commit` 开分支 `feat/<id>`。分支已存在就重建，保证幂等。
2. 拼 prompt。内容：任务单路径、需求原文、验收标准、不在范围的事、以及一句硬约束——「只改这个仓库，改动留在当前分支，不要合并，不要碰主干」。
3. `codex exec --sandbox workspace-write --cd <后端仓库> <prompt>`。
   - 沙箱必须开。无人值守，它不会问你。
   - 设超时。一小时没结果就杀，标 `failed`，把最后一段 stderr 留下。
4. 检查 `git status --porcelain`。**空的就失败**。codex 什么都没改却报告完成，是常见情况，不能当成功。
5. commit，记下 sha，`push -u origin feat/<id>`。

**状态流转**：`open` → `in_progress` → `delivered`。

**失败处理**：任何一步失败，状态 `failed`，`result.notes` 存最后 4000 字符的输出。**不要把分支删掉**，留着让人看。

---

## 四、合并

**谁做**：同一个进程开 PR。合并由 gate 决定，不由它决定。

**顺序**：

1. `gh pr create --base dev --head feat/<id>`。PR 正文用 requirement 加验收标准，评审的人不用再去翻任务单。
2. 等 CI。CI 超时就标 `merge_failed`，不硬合。
3. **三个 gate 条件，全满足才自动合**：
   - CI 全绿
   - rebase 到最新 dev 无冲突
   - 改动路径都在 `out_of_scope` 之外

   有一条不满足，状态留 `awaiting_merge`，等人工。这是整套东西里唯一必须留人的地方——无人值守的 codex 不知道 dev 上压着谁的活。
4. 合并：`gh pr merge --squash --auto`。

**为什么不做本地 `git merge`**：本地 merge 要 checkout，就要动工作区。任何人手上有未提交的改动，流程就断在那儿。走 API 完全不碰工作区。

**dev 有直推怎么办**：有人直接 push 到 dev，那条提交没过 CI，dev 的绿就不可信。能加分支保护就加；加不了，至少挂一条 post-push CI，红了立刻告警。

**状态流转**：`delivered` → `merging` → `merged`。

---

## 五、部署对齐

dev 合进去自动触发部署。这一步要解决的是：**你验收的到底是哪一版代码**。

**做法**：轮询 dev 环境的版本接口，等它报的 commit 等于 `result.commit_sha`，才算部署完成。间隔 5 秒，超时 15 分钟。

**版本接口怎么做**，三个方案按成本排：

- **加一个 `/version` 返回 `{ sha }`**。最好，五行代码。没有的话后面全是猜。
- **CI 部署完把 sha 写进 dev 服务器的一个静态文件**（比如 `/.version`），前端读它。不用改后端代码，但要动 CI。
- **完全不改**，用 `git ls-remote origin dev` 确认合并了就算完成，部署状态人工确认。**这是降级，不是等价**——你验的可能是旧版本。

**部署必须串行加锁**。两个人在五分钟内先后合并，第二次要排队，不能并发。并发部署会互相覆盖，最后跑的是哪个谁也说不清。

**超时怎么办**：状态标 `merged`，`deploy_sha` 写 `timeout`。前端此时应该报告「部署没完成」，而不是「验收通过」。

---

## 六、验收

**触发**：前端跑 `/deliver <id>`。

**顺序**：

1. `git pull` 拿最新的任务单，读 `tasks/<id>.json`。状态不是 `merged` 就说明还没交付完，报告当前状态，继续等。
2. 等状态变化，两条路选一条：
   - 装了加速器就订阅 SSE。断了退回第下一档。
   - 没有加速器就每两秒 `git ls-remote` 探一次。慢几秒，但零依赖、不会被休眠掐断。
3. 状态到 `merged` 之后，对版本接口发 GET，拿它报的 sha 跟 `result.commit_sha` 比前七位。对不上就是部署还在跑，继续等，别急着跑检查。
4. 跑 `acceptance.checks`。每条命令单独执行，`{{base_url}}` 替换成验收环境地址。
5. 逐条报 PASS / FAIL，失败的附输出原文。

**三种结果的处置**：

- **全绿**：把后端交付接回前端会话，按 `contract` 对齐调用代码。
- **有失败**：贴失败命令和输出原文，**附上 `deploy_sha`**。如果这个 sha 跟你验收时记的不一样，八成是别人合进来的改动改了接口行为，不是后端没做好。这句话能省掉很多无效争论。
- **后端 `failed`**：贴 `result.notes` 原文，那是后端 codex 的报错。

**状态流转**：`merged` → `verified`。

---

## 状态机

```
open → in_progress → delivered → merging → merged → verified
         ↓              ↓           ↓
      failed       awaiting_merge  merge_failed
```

`failed` / `merge_failed` 修完可以回到 `in_progress`，但换新 id，别复用——复用会让历史追溯断掉。

---

## 失败场景对照

| 场景 | 现象 | 处理 |
|---|---|---|
| 交接仓推不上去 | push 被拒 | 任务单留本地，能推时再推，别另开通道 |
| codex 没改动 | status 干净 | 判 failed，别当成功 |
| codex 超时 | 一小时后无输出 | 杀掉，留 stderr，分支保留 |
| push 被拒 | 非快进 | `--force-with-lease` 重试一次，再失败就停 |
| CI 红 | PR checks 失败 | `merge_failed`，不硬合 |
| 部署超时 | 版本 sha 一直不匹配 | 标 timeout，让前端知道没验成 |
| 验收不过 | checks 有 FAIL | 贴原文加 deploy_sha，回给后端 |
| dev 环境漂移 | 验收中途别人合了东西 | 报告里带当前 dev sha，先怀疑环境不是代码 |

## 落地顺序

别一次做完。分三步，每步都能用。

**第一步，只做人工通道。** 交接仓 + 任务单格式 + 两个 prompt。前端发起靠人跑，后端执行靠人跑。不做进程、不做队列、不做自动合并。这一步解决「说不清楚」的问题，收益最大，成本最低。

**第二步，加自动执行。** 后端起个常驻进程，扫仓库、排队、拉 codex。仍然人工合并。这一步省掉后端等人的时间。

**第三步，加自动合并和部署对齐。** gate 条件、PR、版本轮询。这一步最容易出问题，所以放最后——前两步跑稳了，再上这层。

---

## 装这两个 prompt

两个文件在 `prompts/`：`handoff.md`、`deliver.md`。

复制到 `~/.codex/prompts/`，然后把里面的 `<交接仓路径>` 换成实际路径。两处都换。换完在 codex 里就能用 `/handoff` 和 `/deliver`。

它们只是指令，不调任何脚本。codex 自己读写任务单、自己跑 git、自己发 HTTP 请求。

---

## 不做什么

不同步 `~/.codex/sessions`。会话是 zstd 压缩的本地 rollout，跨机器 cwd 和模型版本对不上，`resume` 必崩。交接的是任务单加代码。

不自动推主干。

不共享 codex 登录态。每台机器自己的。
