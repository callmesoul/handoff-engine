# Handoff Studio（后端专用）

> 本插件只部署在后端执行机；前端部署不安装。

Handoff Studio 在后端原任务面板之外，把**实现执行器换成了 DSH 自己**：用面板里选定的
模型跑任务实现，而不是拉起 `codex` / `zcode` 子进程。

## 它解决什么

原来任务面板只有两条执行路径，模型来自 `config/*.yaml` 和 `~/.codex/config.toml`。
Handoff Studio 把执行器接到 DSH 的模型目录上：你在面板顶部选 provider / model /
思考程度，任务就用那个模型跑。

执行器换了，**交付流程没换**：认领、隔离 worktree、路径 gate、提交、推送、PR、
部署对齐、验收依旧是 `handoff` 原来那条链路。所以 Studio 跑出来的任务与原面板
跑出来的通过同一套检查。

## 怎么用

1. 左侧边栏点「工作台」，进入任务面板。
2. 顶部选模型（模型清单来自 DSH 当前可路由的模型；选模型后思考档位会跟着换）。
3. 在列表里点一个任务，右侧抽屉显示需求、事件时间线、历史日志。
4. 点「执行」，任务用当前选定的模型开始跑；执行横幅实时显示日志。
5. 执行中可以在横幅下方的输入框里「打断并续跑」；结束后可以「续话」接着派活。

## 与原面板的关系

两套面板读同一个交接仓，可以同时开着，互不影响：

| | 原面板 `handoffctl panel` | Handoff Studio |
| --- | --- | --- |
| 执行器 | `codex` / `zcode` 子进程 | **DSH Agent**（`codex` / `zcode` 仍可选） |
| 模型来源 | `config/*.yaml`、`~/.codex/config.toml` | DSH 宿主实时模型目录 |
| 界面 | 面板自己发的 HTML | DSH 原生 React 面板 |
| 引擎端口 | 8790 | 8791 |

原面板的代码与执行器表都没被修改。

## 模型选的到底是什么

选中的 provider / model / effort 被记录在 `.handoff-run/studio-state.json` 的
`studio` 键里，重启面板后仍在；下一个任务开始执行时使用。每个模型支持的思考程度
不同，选了该模型不支持的档位会被明确拒绝，不会静默改成别的值。

## 额度用完了怎么办：后备模型链

全自动配置里可以按优先级排一列「后备模型」。执行时按「主模型 → 候选 1 → …」试下去，
直到有一个跑通。

换不换的判定不看文案，看宿主给的结构化失败码（`turn/end.reason.error.code`，来自
`@deepseek-ai/dsh-llm` 的 `LLM_FAILURE_CODES`）：额度用尽、限流、鉴权失效、模型不可用、
服务端故障 → 换下一个；内容被拒、请求非法、被取消、超时、agent 自己报 blocked → 不换。
拿不到稳定码时才退回看 HTTP 状态和少数措辞，两者都没有就不换——宁可一次明确失败，也
不要把任务本身的问题拖成好几次重跑。

两个关键设计点：**换模型不接续上一个模型的会话**（那个会话绑的就是刚失败的模型），
**整条链写同一个 attempt 的日志**（人看到的是一轮里发生了什么）。候选全部失败时，
失败原因逐个列出，不会只剩一句「没有结构化结果」。

## 需要知道的限制

- **单并发。** 同一时刻只跑一个任务，与原 worker 一致；第二个请求会被拒绝。
- **执行组成固定为 `standard`。** Agent 的实现能力（shell、写文件）来自它绑定的
  preset；不绑定就会继承发起会话的组成，从分析型会话发起的任务会没有工具可用。
  插件在 Agent 发布**之前**把 `agentPreset`（默认 `standard`）挂上去，挂不上直接失败。
  续跑时优先沿用会话日志里记录的那个组成（上一轮跑的是什么就接着用什么），只有它
  已经不在本机花名册里时才退回配置值，并在日志里说明降级原因。
- **无人值守审批。** 任务跑起来时没人守着那个会话，所以审批策略必须是不询问。
  只有「完全权限」这一档的预设自带免审批，选它时插件走 DSH 的权限服务切到该
  预设，顶部显示「完全权限」；选「只读 / 工作区可写」时插件只写沙箱档位、再把
  审批强制设为不询问——隔离照样生效，代价是顶部显示 `Custom`（这两个旋钮的
  组合在 DSH 的预设表里没有名字，属于正常现象，不是没切成功）。
- **Dsh 执行器健康检查依赖插件。** 插件没启用时，面板仍能看列表、详情、日志，
  但「执行」会报错说明原因。
- **引擎由插件按需拉起。** 面板第一次请求时才启动，插件卸载时收掉；不需要手工
  起 Python 进程。端口已被占用时直接复用已在监听的引擎，不会叠第二个。
- **状态与界面按 DSH 的实际能力收窄。** 核心闭环（列表、详情、执行、实时日志、
  中断/续话、全自动配置、验收按钮）已可用。
- **完成通知由引擎自己投递。** `handoff` 的完成事件是 store 只写本机 outbox、
  再由独立的 `handoffctl notifier` 常驻进程签名投递的两段式流程。原面板由启动脚本
  把两段都拉起来；studio 引擎是插件 spawn 的单个进程，所以它自己带了一个投递线程，
  否则「恢复推进 / 验收」把任务推到 `verified` 之后前端收不到任何事件。
  顶栏的「通知 pending N」就是它的状态，点一下立刻发一轮。
  历史积压不会被自动重发（有水位），需要时用「重发完成通知」。

## 配置

```yaml
- id: handoff-studio
  config:
    enginePort: 8791
    pythonPath: 'C:\Users\you\code\handoff-engine\.venv-win\Scripts\python.exe'
    engineRoot: 'C:\Users\you\code\handoff-store'
    runTimeoutMs: 3600000
```

完整说明见包内 `README.md`。
